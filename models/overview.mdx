## 统一调用方式

以上三个图像模型使用同一接口：

```text
POST https://api.vizluma.online/v1/images/generations
```

在请求体中替换 `model`，其他核心字段保持一致。不要添加未经本账号确认的模型后缀或线路名称。

## 如何选择

先用你自己的代表性业务提示词，比较指令遵循、文字准确率、生成耗时与成本。同一提示词会存在随机差异，单张样例不能用来证明固定画风或判断模型优劣。

这些名称是 Vizluma API 的调用标识。本文不以模型名称、输出尺寸或单张样图证明底层模型身份，也不承诺未经验证的原生高分辨率能力。

## GPT-6.1 Sol 文本接入

模型 ID 为 `gpt-6.1-sol`，使用同一企业 API Key 和 Base URL。支持 Chat Completions 与 Responses 的基础文本请求及 SSE 流式返回。每百万 Token 普通输入 **2 元**、输出 **10 元**、缓存命中输入 **0.10 元**，VIP 八折；完整规则见 [计费说明](/pricing)。

### Chat Completions

先在自己的服务端设置 `VIZLUMA_API_KEY`。示例默认请求 API 域名，也允许通过 `VIZLUMA_BASE_URL` 指定含 `/v1` 的地址：

```bash chat.sh
set -euo pipefail
: "${VIZLUMA_API_KEY:?请先设置 VIZLUMA_API_KEY}"
BASE_URL="${VIZLUMA_BASE_URL:-https://api.vizluma.online/v1}"
curl --fail-with-body --silent --show-error --max-time 120 \
  "${BASE_URL%/}/chat/completions" \
  -H "Authorization: Bearer ${VIZLUMA_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-6.1-sol","messages":[{"role":"user","content":"Reply with exactly OK."}],"reasoning_effort":"low","max_completion_tokens":128,"stream":false}'
```

读取 `choices[0].message.content`，用量见 `usage`。需要流式时，将 `stream` 设为 `true`，增加 `"stream_options":{"include_usage":true}`，并给 curl 加 `--no-buffer`；逐条读取 SSE 的 `data:`，以 `[DONE]` 结束。不要将整个 SSE 当成单个 JSON。

### Responses

```bash responses.sh
set -euo pipefail
: "${VIZLUMA_API_KEY:?请先设置 VIZLUMA_API_KEY}"
BASE_URL="${VIZLUMA_BASE_URL:-https://api.vizluma.online/v1}"
curl --fail-with-body --silent --show-error --max-time 120 \
  "${BASE_URL%/}/responses" \
  -H "Authorization: Bearer ${VIZLUMA_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-6.1-sol","input":"Reply with exactly OK.","reasoning":{"effort":"low"},"max_output_tokens":128,"store":false,"stream":false}'
```

非流式响应从 `output` 中读取 `type=message` 的 `content`，提取 `type=output_text` 的 `text`。需要流式时设 `stream:true` 并使用 `--no-buffer`，处理 `response.output_text.delta`，检查最终 `response.completed` 及其 `usage`；同时处理错误或不完整状态，不要把连接断开当成成功完成。

输出上限也包含推理用量。示例只用于最小联调，复杂任务请按业务需要设置合理上限。基础文本联调不代表工具调用、结构化输出、文件、多模态、长上下文或 WebSocket 均已验收；这些能力请先与对接人员确认。`gpt-6.1-terra` 当前未开放。

视频与图片接口不同：**创建任务后立即返回任务 ID，由客户端轮询到完成再下载**，不在创建请求里等待完整 MP4。不使用 Chat Completions 或 Responses 来创建这六个视频模型。

### 第一步：创建任务

先在服务端设置 `VIZLUMA_API_KEY`。每次执行以下脚本都会创建一个新任务，可能收费；不要因网络超时自动重发。

```bash video-create.sh
set -euo pipefail
: "${VIZLUMA_API_KEY:?请先设置 VIZLUMA_API_KEY}"
BASE_URL="${VIZLUMA_BASE_URL:-https://api.vizluma.online/v1}"
curl --fail-with-body --silent --show-error --max-time 60 \
  "${BASE_URL%/}/videos" \
  -H "Authorization: Bearer ${VIZLUMA_API_KEY}" \
  -H "Content-Type: application/json" \
  -d '{"model":"seedance-2.5-480p","prompt":"A cat walking slowly on a sunny beach, gentle waves in the background","duration":5,"ratio":"16:9","resolution":"480p"}' \
  --output video-task.json
cat video-task.json
```

保存响应中的 `id`，后续只使用这个本站任务 ID，不能使用其他平台的 ID。HTTP 状态以实际响应为准；成功响应包含 `object: "video"` 与任务状态。

### 第二步：查询状态

把创建响应的 `id` 设置为服务端环境变量 `VIDEO_ID`，执行以下查询；建议每30秒查询一次，不要循环创建任务。

```bash video-status.sh
set -euo pipefail
: "${VIZLUMA_API_KEY:?请先设置 VIZLUMA_API_KEY}"
: "${VIDEO_ID:?请设置创建响应中的 id}"
BASE_URL="${VIZLUMA_BASE_URL:-https://api.vizluma.online/v1}"
curl --fail-with-body --silent --show-error --max-time 60 \
  "${BASE_URL%/}/videos/${VIDEO_ID}" \
  -H "Authorization: Bearer ${VIZLUMA_API_KEY}"
```

- `queued` / `in_progress`：继续查询。
- `completed`：可以下载。
- `failed`：停止轮询，核对错误及最终退款记录。
- 未识别的状态、查询超时或暂时错误：保留任务 ID，核对任务与调用记录，不要把它当成创建失败立即重发。

### 第三步：下载 MP4

仅在任务状态为 `completed` 后执行。结果不保证永久保存，请及时转存到企业自己的存储。

```bash video-download.sh
set -euo pipefail
: "${VIZLUMA_API_KEY:?请先设置 VIZLUMA_API_KEY}"
: "${VIDEO_ID:?请设置已完成任务的 id}"
BASE_URL="${VIZLUMA_BASE_URL:-https://api.vizluma.online/v1}"
curl --fail --silent --show-error --max-time 600 \
  "${BASE_URL%/}/videos/${VIDEO_ID}/content" \
  -H "Authorization: Bearer ${VIZLUMA_API_KEY}" \
  --output video.mp4
```

下载需要同一企业账户的有效 Key；不要把带凭据的请求转发给第三方地址。可按标准 `Range` 请求分段下载；当前尚未进行真实视频的 Range 联调。

### 参数与参考素材

仅接受 JSON。必填 `model`；`prompt` 为文本提示词，提供首帧或参考素材时可以省略。

- `duration`：正整数秒，默认5秒，不能使用 `-1` 自动时长；可使用 `seconds` 作为别名，两者同时传入时必须一致。
- `ratio`：默认 `16:9`；允许 `16:9`、`9:16`、`1:1`、`4:3`、`3:4`、`21:9`、`adaptive`，最终支持情况以所选模型为准。
- `resolution`：可省略；传入时必须匹配模型固定分辨率，不能通过这个字段改变计费规格。
- `first_frame` / `last_frame`：公网 HTTP(S) 图片 URL，或 `{ "image_url": "https://…" }`；尾帧必须同时有首帧。
- `reference_images`：URL 字符串或 `image_url` 对象组成的数组；2.0最多9张，2.5最多30张。
- `reference_videos` / `reference_audios`：分别最多10项，可用 URL 字符串，或含 `video_url` / `audio_url` 的对象。音频单段至少1.8秒、总长不超过30秒等媒体约束由上游校验，请先确认具体模型能力。
- 首尾帧模式不能与任何参考素材数组混用。暂不支持本地文件、Base64、multipart、批量参数 `n` 或任意 `metadata` 透传；未声明字段会被拒绝，避免影响时长与费用。

有模型白名单的企业 Key 需要管理员单独开通对应视频模型；现有 Key 不会因新增渠道自动扩大白名单。
